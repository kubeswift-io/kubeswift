# v0.15.0 Release Validation

v0.15.0 was validated on three lab clusters before it was tagged. The
release-blocking scenarios passed on the final candidate, `8afbad3`. The
tagged commit differs from it only in documentation.

This page summarises the validation. The full plan and every report are on
the branch
[`validation/v0.15.0-candidate`](https://github.com/kubeswift-io/kubeswift/tree/validation/v0.15.0-candidate/docs/validation/v0.15.0-candidate):
`PLAN.md`, and `phase<N>[-r<round>].md` for each phase of each round.

## Clusters

| Cluster | Kubernetes | What it covers |
|---|---|---|
| dev | `v1.34.3+k0s`, 3 nodes, all KVM-capable | Longhorn (RWX Block, live migration) and Rook Ceph; one GPU; the full suites |
| sov | `v1.35.3+k0s`, 3 nodes | An install without the admission webhook: controller, VAPs, gateway console grant |
| ntx | `v1.34.9` (kubeadm), OVN-Kubernetes primary network | Guests on a primary UDN, including CAPI-managed ones that must stay untouched by an upgrade |

## Method

**Each round** upgraded all three clusters to the candidate's dev build:
chart `0.0.0-dev.<sha>`, images `sha-<sha>`, and CRDs applied first. It then
ran:
- **Phase 1:** the upgrade itself, with pre-checks and baselines. Long-running
  guests on dev and ntx had to keep the same launcher UID, with 0 restarts.
- **Phase 2:** the dev suites.
- **Phase 3:** the ntx and sov checks.

**Stop condition.** A guest left without a running VM stops the round at once.
That happened once, in round 1.

**Every guest a scenario used was created after the upgrade**, so it ran the
candidate's launcher.

## What the final round checked (`8afbad3`)

- **Upgrade (all three clusters).**
  - No guest was stopped by the new `runPolicy` handling.
  - Guests `Failed` on a failed image stay `Failed` and get no pod.
  - The controller can list events.
  - `--metrics-secure=true` survives the upgrade.
  - The GPU warm slot and the long-running guests are undisturbed.
- **R7-D.**
  - A live migration of a Longhorn volume with a replica still rebuilding fails
    `DstNeverReady` at 60 s, naming `PVC "…" not attached to node <target>
    (VolumeAttachment …)`.
  - The guest stays running on its source: same launcher, no reboot, data
    intact.
- **V4a live.** `test/migration/migration-test.sh --mode live` passed: it waits
  for a healthy Longhorn volume, the tmpfs sentinel survives, and uptime keeps
  counting.
- **N3 and S1.**
  - The CAPI control-plane guest on ntx is not written by the upgrade.
  - The sov controller, VAPs and gateway console grant are as expected.

## Covered by the earlier rounds on the same code paths

**Live migration:**
- cancel mid-transfer (T3);
- cancel racing completion, three times back to back (T5);
- a migration right after a cancel to a busy node (V6);
- pinned-guest repin (V4b);
- the `DestinationRunning` phaseDetail (V5).

**Other features:**
- `runPolicy: Stopped`, including `StopDeferred` during a migration (V3);
- snapshot namespace deletion (V8);
- in-place restore keeping its address (R2, V11);
- guest and pod IPs (V2);
- kernel re-pull after an upgrade (V10);
- the sandbox and warm-pool fixes (R5-C, V9);
- guests waiting for missing or importing images, and pools not churning (R6-A to R6-F);
- smoke on every boot path (V1).

## Known issues, tracked after v0.15.0

- **#692.** After a failed live migration, Longhorn can finish attaching the
  volume to the target and keep that attachment for a few minutes, with no pod
  there. The guest is unaffected. `docs/migration/troubleshooting.md` says to
  wait for it to clear before retrying.
- **#694.** A migration refused at validation, for example `ImageTagMismatch`,
  records no Warning event, only its condition.
- **#672.** Two guests on one node can share a guest IP on the nat network (the
  per-launcher bridge range). `status.network.podIP` and `primaryIPScope` tell
  them apart. Cluster-unique addresses (IPAM) are on the roadmap.
- **Guest PodDisruptionBudgets log `CalculateExpectedPodCountFailed`.**
  Eviction is still blocked as intended (`disruptionsAllowed` is 0). This is
  event noise that predates v0.15.0.
- **The UI console's browser check is manual** and is not part of these
  reports.
